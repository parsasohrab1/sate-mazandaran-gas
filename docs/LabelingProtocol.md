# پروتکل برچسب‌گذاری و بازبینی (Labeling Protocol)

این پروتکل تضمین می‌کند که برچسب‌های داده واقعی شرکت گاز استان مازندران
تکرارپذیر، قابل حسابرسی و منطبق با استانداردهای فنی باشند.

## ۱. دامنه و هدف

این پروتکل بر داده رادیوگرافی جوش خطوط لوله اعمال می‌شود که برای آموزش و
ارزیابی مدل تشخیص عیوب استفاده می‌شود. هدف: تولید برچسب با توافق بین‌کارشناس
(inter-rater agreement) بالا و قابل ردیابی برای تحلیل علل (CAR) در CMMI ML5.

## ۲. نقش‌ها

| نقش | مسئولیت |
|-----|---------|
| Labeler-۱ (کارشناس NDT سطح II) | برچسب‌گذاری اولیه |
| Labeler-۲ (کارشناس NDT سطح III) | برچسب‌گذاری مستقل دوم |
| Adjudicator (سرپرست بازرسی) | حل اختلاف بین دو برچسب |
| Data Steward | ثبت متاداده، نگهداری manifest |

## ۳. طبقه‌بندی عیوب

کلاس‌ها و شرح بصری در [`DataDictionary.md`](DataDictionary.md) §۱ آمده است.
مبنای طبقه‌بندی: **API 1104** (Acceptance Standards) و **ASME Section V**
(Article 2). هر تصویر دقیقاً یک برچسب اصلی دریافت می‌کند (multi-class).

## ۴. گردش کار برچسب‌گذاری

```
1. intake     ← تصویر + متاداده (segment, pipeline_id, date) در manifest
2. label-A    ← Labeler-۱ برچسب می‌زند (ابزار: dashboard یا CSV)
3. label-B    ← Labeler-۲ مستقل برچسب می‌زند (کور نسبت به A)
4. compare    ← اگر A==B → برچسب نهایی؛ اگر A≠B → Adjudicator
5. adjudicate ← Adjudicator برچسب نهایی را ثبت + دلیل اختلاف
6. lock       ← برچسب نهایی در manifest با ستون label + reviewer + adjudicated
```

## ۵. معیار توافق بین‌کارشناس (Inter-Rater Agreement)

- **Cohen's Kappa** بین Labeler-۱ و Labeler-۲ محاسبه می‌شود (`utils/metrics.py`).
- **هدف:** κ ≥ ۰٫۸۰ (توافق قوی). اگر κ < ۰٫۷۰، پروتکل بازبینی و آموزش مجدد می‌شود.
- κ به‌صورت دوره‌ای در `metrics/latest/labeling_agreement.json` گزارش می‌شود (OPP).

## ۶. کنترل کیفیت

- **نمونه‌گیری دورانی:** ۱۰٪ برچسب‌های نهایی توسط سرپرست بازرسی دوباره بررسی می‌شوند.
- **تصاویر مرزی (edge cases):** تصاویری با اطمینان مدل پایین، به‌صورت فعال
  برای re-labeling اولویت‌دار می‌شوند (active learning).
- **حل اختلاف:** هر مورد اختلاف با دلیل متنی ثبت می‌شود (CAR feed).

## ۷. متاداده هر برچسب

هر رکورد در manifest (نسخه برچسب‌خورده) شامل:

| ستون | شرح |
|------|------|
| `image` | نام فایل |
| `label` | برچسب نهایی |
| `labeler_1` | برچسب اول |
| `labeler_2` | برچسب دوم |
| `adjudicated` | bool — آیا اختلاف حل شده؟ |
| `adjudicator` | نام حل‌کننده (در صورت اختلاف) |
| `disagreement_reason` | دلیل اختلاف (متن) |
| `confidence_labeler` | اطمینان خودکارشناس (۱-۵) |
| `segment`, `pipeline_id`, `date` | متاداده عملیاتی |

## ۸. محرمانگی و امنیت

- تصاویر واقعی فقط در محیط کنترل‌شده قابل مشاهده هستند.
- دسترسی به ابزار برچسب‌گذاری با نقش RBAC محدود می‌شود.
- خروجی (manifest بدون پیکسل) قابل ذخیره در git است؛ تصاویر هرگز.

## ۹. بازآموزی و بهبود پروتکل

- هر فصل، κ و نرخ اختلاف بازبینی می‌شود (OID/CAR).
- اگر کلاسی κ پایین داشته باشد، راهنمای بصری آن کلاس بهبود می‌یابد.
- تغییرات پروتکل با نسخه در `docs/LabelingProtocol.md` ردیابی می‌شود (PAL).

## ۱۰. ابزار

- برچسب‌گذاری: داشبورد داخلی (`dashboard/index.html` با حالت label) یا
  ابزار خارجی (CVAT/Label Studio) با خروجی CSV هم‌ساخت با manifest.
- محاسبه κ: `python scripts/compute_kappa.py manifest.csv`.
