## ۱. مقدمه

### ۱.۱ هدف
این سند نیازمندی‌های نرم‌افزاری محصول تشخیص و طبقه‌بندی عیوب جوش خطوط لوله
را به‌صورت کامل، غیرابهامی و قابل آزمون بیان می‌کند. مخاطبان: تیم مجری،
کارفرما، کارشناسان NDT و واحد IT.

### ۱.۲ دامنه
نرم‌افزار شامل: بارگذاری و پیش‌پردازش تصاویر رادیوگرافی، آموزش و ارزیابی
مدل‌های یادگیری ماشین، خدمت‌رسانی پیش‌بینی از طریق API و داشبورد، و زیرساخت
MLOps برای ردیابی و پایش. **خارج از دامنه:** تصمیم‌گیری خودکار ایمنی بدون
تأیید کارشناس، کنترل دستگاه‌های بازرسی فیزیکی.

### ۱.۳ تعاریف و مخفف‌ها
- NDT: Non-Destructive Testing — آزمون‌های غیرمخرب
- ML/MLOps: یادگیری ماشین / عملیاتی‌سازی آن
- F1/ROC/AUC: معیارهای ارزیابی طبقه‌بندی
- MLflow: پلتفرم ردیابی آزمایش‌ها و رجیستری مدل
- API: رابط برنامه‌نویسی اپلیکیشن (REST)
- OPP/QPM/CAR: فرآیندهای CMMI ML5 (مشاهده [CMMI_ML5/](CMMI_ML5/00_overview.md))

### ۱.۴ ارجاعات
API 1104، ASME Section V، ASME Section VIII، ASME B31.3، IEEE 830، CMMI V2.0، RFC 7807 (Problem Details).

### ۱.۵ نمای کلی
بخش ۲ الزامات کلی، بخش ۳ نیازمندی‌های کارکردی، بخش ۴ نیازمندی‌های رابط،
بخش ۵ نیازمندی‌های غیرکارکردی، بخش ۶ محدودیت‌ها و الزامات طراحی.

## ۲. توصیف کلی

### ۲.۱ پیش‌فرض محیط محصول
محصول به‌صورت سرویس REST + داشبورد ایستا روی زیرساخت داخلی شرکت گاز استان
مازندران (Linux/Kubernetes) مستقر می‌شود. تصاویر ورودی از سیستم آرشیو NDT
کارفرما تأمین می‌شود.

### ۲.۲ ویژگی‌های کاربر
| کاربر | شرح | سطح دسترسی |
|-------|------|------------|
| کارشناس NDT | مشاهده پیش‌بینی‌ها، تأیید/رد | read+annotate |
| سرپرست بازرسی | مشاهده داشبورد، گزارش‌گیری | read+export |
| مهندس ML | آموزش، ارزیابی، استقرار مدل | admin (ml) |
| مدیر IT | مدیریت زیرساخت و امنیت | admin (infra) |

### ۲.۳ محدودیت‌ها
- پایتون ≥ ۳.۱۰؛ وابستگی‌ها مطابق `requirements.txt`.
- پشتیبانی از CPU و GPU (CUDA)؛ اجرا باید روی CPU میزبان کارفرما ممکن باشد.
- عدم ذخیره تصاویر واقعی در git یا MLflow artifacts (محرمانگی).

### ۲.۴ وابستگی‌ها
MLflow برای ردیابی، FastAPI برای خدمت‌رسانی، Docker/K8s برای استقرار،
DVC برای نسخه‌گذاری داده (اختیاری).

## ۳. نیازمندی‌های کارکردی (Functional Requirements)

### FR-1 — بارگذاری و پیش‌پردازش داده
- **FR-1.1** سیستم باید تصاویر رادیوگرافی با قالب PNG/JPG/BMP/TIFF/DICOM را بارگذاری کند.
- **FR-1.2** سیستم باید پایپ‌لاین پیش‌پردازش (denoise → CLAHE → resize → normalize) را به‌صورت تکرارپذیر اجرا کند (`weld_defect.data.preprocess`).
- **FR-1.3** سیستم باید تقسیم train/val/test را به‌صورت **stratified-group** انجام دهد تا نشت داده از یک قطعه جوش بین اسپلیت‌ها رخ ندهد.
- **FR-1.4** سیستم باید پروفایل کیفیت داده (imbalance ratio، تعداد تصاویر گمشده) را تولید کند (`data_profile.json`).

### FR-2 — آموزش مدل
- **FR-2.1** سیستم باید چهار معماری را پشتیبانی کند: CustomCNN، ResNet50، EfficientNet-B0، Ensemble.
- **FR-2.2** سیستم باید آموزش را با focal loss (برای عدم توازن کلاس) و AdamW + cosine warmup انجام دهد.
- **FR-2.3** سیستم باید هر اجرا را در MLflow ثبت کند (پارامترها، معیارها، آرتیفکت).
- **FR-2.4** سیستم باید early stopping روی `val_f1_macro` با patience قابل تنظیم داشته باشد.
- **FR-2.5** سیستم باید قابلیت تکرار را با `seed_everything` تضمین کند.

### FR-3 — ارزیابی و اعتبارسنجی
- **FR-3.1** سیستم باید معیارهای accuracy، balanced_accuracy، F1-macro، precision/recall macro، Cohen's kappa، MCC، ROC-AUC OvR را محاسبه کند.
- **FR-3.2** سیستم باید ماتریس درهم‌ریختگی و گزارش per-class را تولید کند.
- **FR-3.3** سیستم باید **دروازه‌های پذیرش** BRS §6 را ارزیابی کرده و pass/fail گزارش کند.
- **FR-3.4** سیستم باید نمونه‌های اشتباه‌طبقه‌بندی‌شده را برای تحلیل علل (CAR) تفکیک کند.

### FR-4 — خدمت‌رسانی پیش‌بینی (Inference API)
- **FR-4.1** سیستم باید یک سرویس REST با نقاط انتهایی `GET /health`، `POST /predict`، `POST /predict/batch` ارائه دهد.
- **FR-4.2** پاسخ هر پیش‌بینی باید شامل کلاس پیش‌بینی‌شده، top-k احتمالات، زمان استنتاج و پرچم `decision_support_only=True` باشد.
- **FR-4.3** سیستم باید اندازه آپلود را محدود کند (پیش‌فرض ۱۰ مگابایت، قابل پیکربندی).
- **FR-4.4** سیستم باید مستندات OpenAPI خودکار در `/docs` ارائه دهد.

### FR-5 — داشبورد
- **FR-5.1** داشبورد باید معیارهای لحظه‌ای (F1، recall کلاس ترک، زمان استنتاج) و ماتریس درهم‌ریختگی را نمایش دهد.
- **FR-5.2** داشبورد باید تاریخچه MLflow runs و وضعیت دروازه‌های پذیرش را نشان دهد.

### FR-6 — مدیریت مدل و MLOps
- **FR-6.1** سیستم باید رجیستری مدل MLflow را نگهداری کند (Staging/Production).
- **FR-6.2** سیستم باید تشخیص انحراف (drift) داده ورودی را با Evidently اجرا کند.
- **FR-6.3** سیستم باید یک DAG هوازیر (Airflow) برای بازآموزی دوره‌ای ارائه دهد.

## ۴. نیازمندی‌های رابط (Interface Requirements)

### ۴.۱ رابط کاربری
داشبورد HTML ایستا با نمودارها (ECharts). کارشناس می‌تواند تصویر بارگذاری کرده
و پیش‌بینی + تأیید/رد را ثبت کند.

### ۴.۲ رابط سخت‌افزار
بدون رابط مستقیم سخت‌افزار؛ تصاویر از فایل سیستم/آرشیو خوانده می‌شوند.

### ۴.۳ رابط نرم‌افزاری (API)
REST/JSON روی HTTP؛ احراز هویت با API Key (هدر `X-API-Key`). جزئیات در [API.md](API.md).

### ۴.۴ رابط ارتباطی
HTTPS داخلی؛ برای انتقال داده‌های حجیم از فایل سیستم مشترک یا S3-compatible storage استفاده می‌شود.

## ۵. نیازمندی‌های غیرکارکردی (Non-Functional Requirements)

### ۵.۱ عملکرد (Performance)
- **NFR-P1** زمان استنتاج ≤ ۱۲۰ ms/تصویر روی یک هسته CPU میزبان.
- **NFR-P2** توان عملیاتی ≥ ۱۰ تصویر/ثانیه روی GPU واحد در حالت batch.
- **NFR-P3** زمان راه‌اندازی سرویس ≤ ۳۰ ثانیه.

### ۵.۲ قابلیت اطمینان (Reliability)
- **NFR-R1** سرویس با HA دو نمونه همزمان deploy شود.
- **NFR-R2** نرخ خطای HTTP 5xx < ۰٫۵٪ در روز.

### ۵.۳ امنیت (Security)
- **NFR-S1** احراز هویت همه نقاط انتهایی نوشتنی با API Key/JWT.
- **NFR-S2** رمزنگاری در حالت انتقال (TLS) و در حالت استقرار (at-rest برای آرشیو).
- **NFR-S3** لاگ دسترسی به داده واقعی و تفکیک نقش‌ها (RBAC).
- **NFR-S4** اسکن امنیتی خودکار (bandit, trivy) در CI.

### ۵.۴ نگهداشت‌پذیری (Maintainability)
- **NFR-M1** پوشش تست ≥ ۸۰٪ (پیکربندی در `pyproject.toml`).
- **NFR-M2** هر تغییر از طریق PR و pre-commit hooks (ruff/black/mypy/bandit).
- **NFR-M3** دارایی‌های فرآیندی CMMI ML5 برای قابل ردیابی بودن تغییرات.

### ۵.۵ قابلیت حمل (Portability)
- **NFR-PO1** اجرا روی Linux x86_64؛ کانتینر Docker رسمی.
- **NFR-PO2** استقرار با Helm روی Kubernetes.

### ۵.۶ کاربردپذیری (Usability)
- **NFR-U1** داشبورد راست‌چین (RTL) با زبان فارسی.
- **NFR-U2** مستندات کاربری در دسترس غیربرنامه‌نویس.

### ۵.۷ انطباق (Compliance)
- **NFR-C1** رعایت LICENSE اختصاصی (محرمانگی، عدم بازتوزیع).
- **NFR-C2** رعایت استانداردهای فنی مورد توافق (API 1104 و ASME).

### ۵.۴ ایمنی و تصمیم‌گیری (Safety — حیاتی)
> **SFR-Safety-1:** خروجی مدل به‌تنهایی مبنای تصمیم ایمنی نیست. هر
> پیش‌بینی باید با پرچم `decision_support_only=True` برچسب‌گذاری شود و
> تأیید نهایی با کارشناس واجد صلاحیت NDT ثبت گردد. این الزام در API،
> داشبورد و LICENSE بازتاب داده شده است.

## ۶. محدودیت‌ها و الزامات طراحی

- طراحی چندلایه: data → models → MLOps → API → dashboard (مشاهده [Architecture.md](Architecture.md)).
- جداسازی داده/کد: داده در `data/`، کد در `src/`، پیکربندی در `configs/`.
- تزریق وابستگی از طریق `weld_defect.config` (YAML → dataclass).
- همه اسکریپت‌های تولید خروجی در `scripts/` پایدار و قابل تکرار باشند.
